# UI-003 – Kanban-Drag&Drop ohne Tastaturalternative

- **Schweregrad:** Critical
- **Priorität:** P0 – Release blocker
- **Kategorie:** Accessibility (WCAG 2.2 AA – 2.1.1 Keyboard)
- **Fundort:** [app/static/js/kanban.js:115-146](app/static/js/kanban.js)
  (`initDragUndDrop`, native `dragstart`/`dragover`/`drop`-Events),
  gerendert über [app/templates/kanban/_spalten.html:56](app/templates/kanban/_spalten.html)
  (`draggable="true"` auf `.karte`)

## Problem

Der einzige Weg, eine Karte von einer Spalte in eine andere zu bewegen
(z. B. "Offen" → "In Arbeit" → "Erledigt"), ist natives HTML5-Drag&Drop
per Maus. Es gibt keinen Button, kein Kontextmenü, keinen Tastatur-Shortcut
und keine Formular-Alternative, um denselben Effekt ohne Maus zu erzielen.

## Warum das ein Problem ist

- Verstößt gegen WCAG 2.2 AA Kriterium 2.1.1 (Keyboard): jede Funktionalität
  muss per Tastatur erreichbar sein. HTML5-Drag&Drop ist von Natur aus nicht
  tastaturbedienbar und wird von Screenreadern in aller Regel nicht sinnvoll
  angekündigt.
- Kanban ist laut `docs/KONZEPT.md` Abschnitt 2.1 das zentrale,
  alltäglich genutzte Modul der Anwendung ("Maßnahmen der Reha-Maßnahme
  organisieren") – der Kern-Workflow ist für Tastatur-/Switch-Nutzer:innen
  faktisch nicht nutzbar.
- Die Zielgruppe (`docs/KONZEPT.md` Abschnitt 1: "oft mit eingeschränkter
  Belastbarkeit") schließt laut CLAUDE.md-Philosophie ausdrücklich auch
  Menschen mit motorischen Einschränkungen ein, für die Drag&Drop
  besonders schwierig sein kann – nicht nur reine Tastaturnutzer:innen.
- Es gibt zwar bereits die serverseitige Route zum Aktualisieren einer
  Karte (`/kanban/karten/{id}/aktualisieren`), aber kein UI-Element, um
  darüber die Spalte zu wechseln.

## Erwartete Nutzerauswirkung

Kanban wird für alle Nutzer:innen unabhängig von Eingabegerät bedienbar;
schließt eine harte Zugangsbarriere für einen Teil der Zielgruppe.

## Lösungsvorschlag

Pro Karte einen kleinen, per Tastatur erreichbaren "Verschieben nach …"-
Mechanismus ergänzen, z. B.:

- In der bereits vorhandenen Karten-Detailansicht (`<details class="karte">`)
  ein `<select>` mit den Spaltennamen des Boards + "Verschieben"-Button,
  der serverseitig dieselbe Logik wie das Drag&Drop-Reihenfolge-Endpoint
  auslöst (neue Route `POST /kanban/karten/{id}/spalte`, oder Erweiterung
  des bestehenden Aktualisieren-Formulars um ein Spalten-Feld).
- Drag&Drop bleibt für Maus-Nutzer:innen unverändert erhalten – dies ist
  eine Ergänzung, keine Ablösung.
- Fokus-Reihenfolge und `aria-label` des neuen Controls beachten, damit
  auch Screenreader den Zweck ("Karte in andere Spalte verschieben")
  klar ankündigen.

## Aufwand

**L** – Backend-Route + Template-Änderung an `_spalten.html` +
Berechtigungslogik (gleiche Regeln wie Drag&Drop: gesperrte
Erledigt-Karten, `darf_board_verwalten`) müssen konsistent mitgezogen
werden.

## Abhängigkeiten

Sollte dieselbe Sperrlogik für die fest verankerte "Erledigt"-Spalte
respektieren, die bereits in `kanban.js`/`_spalten.html` für Drag&Drop
implementiert ist (`ist_gesperrt`).

## Abnahmekriterien

- [ ] Karte lässt sich vollständig per Tastatur (Tab, Enter/Space,
      Pfeiltasten im Select) in eine andere Spalte verschieben
- [ ] Gesperrte Karten in der Erledigt-Spalte verhalten sich identisch zur
      Drag&Drop-Regel (nur zurückziehen erlaubt, dann entsperrt)
- [ ] Automatisierte a11y-Prüfung (z. B. axe) zeigt keinen 2.1.1-Verstoß
      mehr für die Board-Ansicht
- [ ] Screenreader-Test (NVDA/VoiceOver): Zweck und Ergebnis der Aktion
      werden angekündigt
